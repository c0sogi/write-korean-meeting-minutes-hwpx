# 회의록 작성 원칙

## 1. 목표

대화를 단순 축약하지 않고, 회의 목적·핵심 쟁점·판단 근거·결정·후속 조치를 빠르게 파악할 수 있는 공식 한국어 업무 문서로 재구성한다.

## 2. 출처 우선순위

1. 사용자가 확정한 메타데이터, 수정사항, 화자 매핑, 용어 표기
2. 회의에서 실제로 사용한 참고 자료
3. 타임스탬프와 화자가 있는 전사 구간
4. 전체 전사문
5. 날짜 형식이 명시된 경우에만 파일명 힌트

자료가 충돌하면 사용자가 명시적으로 확정한 내용을 우선한다. 충돌 자체가 중요한 경우에는 검토 항목에 남긴다.

## 3. 근거 분류

- `fact`: 회의에서 확인되거나 설명된 사실
- `proposal`: 아이디어, 선택지, 제안
- `concern`: 반론, 위험, 제약, 실패 가능성
- `decision`: 명시적으로 채택·확정·동의·승인·지시된 내용
- `action`: 수행하기로 한 구체적 업무
- `open_question`: 답이 없거나 다음 논의로 넘긴 사항

같은 의견이 반복되었다는 이유만으로 결정으로 분류하지 않는다. 동의·선택·확정·승인·지시 또는 회의 말미의 명확한 정리가 있어야 한다.

## 4. 시간순 대화를 주제순으로 재구성

1. 전체 전사에서 회의 목적과 큰 흐름을 파악한다.
2. 여러 시점에 흩어진 같은 주제의 발언을 묶는다.
3. 제안 → 우려 → 조정 → 최종 결정의 흐름을 유지한다.
4. 초기 아이디어와 최종 결론이 다르면 최종 결론을 회의 결과에 둔다.
5. 의미 없는 반복, 추임새, 말더듬, 인식 파편, 사적 잡담은 제거한다.
6. 결론의 근거가 되는 기술 제약, 비용, 일정, 책임 범위, 반론은 남긴다.

## 5. 메타데이터

- `Created at`은 전사본 생성 시각이며 회의 일시로 사용하지 않는다.
- 파일명 날짜는 형식이 확정된 경우에만 해석한다.
- 참석자를 전사 화자 수로 추정하지 않는다.
- 책임기관, 장소, 참석인원이 없으면 `확인 필요`로 표시하고 `quality.missing_metadata`에 기록한다.
- 오늘·내일·다음 주 같은 상대 날짜는 회의일이 확정된 경우에만 절대 날짜로 바꾼다.

## 6. 화자와 고유명사

- `A`, `B`, `C`, `[[SPEAKER_1]]`은 실명이 아니다.
- 전사에 이름이 등장해도 해당 발언자의 이름이라고 추정하지 않는다.
- 기관명, 인명, 과제명, 제품명, 영문 약어는 사용자 표기와 참고 자료를 우선한다.
- 음성인식 결과가 모호하면 외부 지식으로 몰래 고치지 않는다.
- 문맥상 꼭 필요하지만 확정할 수 없으면 `[표기 확인 필요: 전사 표현]`으로 남긴다.

## 7. 화면 의존 발언

“여기 그림”, “이걸 밑으로”, “저 회사”, “이 배치” 같은 발언은 슬라이드·문서·이미지가 없으면 구체적인 사실로 바꾸지 않는다.

가능한 표현:

```text
추진체계도 내 기관 배치를 조정하는 방향을 논의함.
구체적인 기관과 위치는 참고 자료 확인이 필요함.
```

피해야 할 표현:

```text
참고 자료 없이 특정 기관을 특정 기술 블록에 확정 배치했다고 작성함.
```

## 8. 문서 구조

### 상단 메타데이터

- 안건
- 일시
- 책임기관
- 장소
- 참석인원
- 주요안건

### 회의 내용

`회의 요지`는 한 문단으로 작성하며 다음을 포함한다.

- 왜 모였는지
- 무엇을 검토했는지
- 가장 중요한 결론 또는 다음 단계가 무엇인지

`2. 주요 논의` 아래에는 보통 3~7개 주제를 둔다.

```text
2.1. 주제명
- 논의 내용
- 판단 근거 또는 제약
- 결정되지 않은 선택지
```

### 회의 결과

`[요약]`에는 확정된 결론과 방향만 둔다.

`[후속 조치]`에는 실행 항목을 둔다.

```text
- 과업 내용 (담당: 확인된 담당자 / 기한: 확인된 기한)
```

담당자나 기한을 확인할 수 없으면 해당 괄호를 생략한다. 추정하지 않는다.

`[확인 필요 사항]`은 실제 문서 활용에 영향을 주는 미확정 정보가 있을 때만 추가한다.

## 9. 문체

- 간결하고 중립적인 업무 문체
- 기본 종결: `-함`, `-하기로 함`, `-필요함`, `-논의됨`, `-판단됨`
- 한 문단에는 하나의 논점만 배치
- 같은 내용을 여러 절에 반복하지 않음
- 대화체, 감정 표현, 과도한 수식 제거
- 의사결정 강도를 근거에 맞게 표현

명시적인 결정이 있을 때만 다음 표현을 사용한다.

```text
확정함 / 선정함 / 진행하기로 함
```

결론이 약하면 다음 표현을 사용한다.

```text
제안됨 / 검토하기로 함 / 필요성이 언급됨 / 추가 확인이 필요함
```

## 10. 제목·굵기·파란색 강조

- 문서 제목 `회 의 록`: 굵게
- `회의 요지`, `2. 주요 논의`, `2.1...`, `[요약]`, `[후속 조치]`: 굵게
- 파란색 `#2F5597`: 중요한 결정, 핵심 결론, 우선순위, 반드시 수행해야 하는 과업의 핵심 구절
- 모든 불릿, 단순 설명, 배경 정보, 문장 전체를 습관적으로 파란색으로 만들지 않음
- 한 중요 문단에 짧은 강조 구절 1개 정도를 권장
- 전체 본문의 파란색 강조 비율이 약 30%를 넘으면 과도한 것으로 검토

JSON 예시:

```json
{
  "text": "세 후보를 선행기술조사한 뒤 최종 후보를 선정하기로 함.",
  "emphasis": ["최종 후보를 선정하기로 함"],
  "important": true
}
```

`important: true`인데 `emphasis`가 비어 있으면 문장 전체가 강조될 수 있다. 가능한 경우 짧은 구절을 직접 지정한다.

## 11. 후속 조치

좋은 예:

```text
기관별 검토 양식을 배포함. (담당: 김담당 / 기한: 2026.07.31. 11:00)
```

근거가 부족한 예:

```text
김담당이 내일 오전까지 모든 부서의 자료를 취합함.
```

전사나 사용자 정보에서 담당자와 기한이 확인되지 않았다면 확정해서 적지 않는다.

## 12. 최종 품질 점검

1. 모든 결정과 후속 조치가 근거 장부에 연결되는가.
2. 제안이나 질문을 결정으로 과장하지 않았는가.
3. 회의 말미의 정리가 앞선 임시 의견보다 우선되었는가.
4. 화자 라벨을 실명으로 바꾸지 않았는가.
5. 회의 일시를 `Created at`에서 가져오지 않았는가.
6. 화면 의존 내용을 참고 자료 없이 구체화하지 않았는가.
7. 불확실한 고유명사와 숫자를 표시했는가.
8. 원본 경로, API 정보, 재실행 명령이 회의록에 들어가지 않았는가.
9. 회의 요지, 주요 논의, 결과, 후속 조치가 모순되지 않는가.
10. 파란색 강조가 핵심 구절에만 제한되었는가.
11. 중요한 반론과 제약이 삭제되지 않았는가.
12. HWPX 내용이 `minutes.json`과 일치하는가.
